`lake build` / elaboration <= 5 min and <= 8 GB (target; anything above is profiled and fixed, never given more heartbeats/timeouts/memory);

### Design (consequences)
1. **Every machine summary of this layer is proved on an Extracted-free library program** `FvModexp.Lib.<Fn><ISA>`
   (generated by `scripts/gen-libprog-sub.py` from the pinned Run extraction: the function's own segments + the segments of its
   callees that are executed inline, stubs, contract addresses; no data). Never on `Extracted.program` (8× slower: kernel
   re-evaluation of the fetch facts over the 84-segment program). Callees' summaries enter via `Summary.of_codeIn`; the
   whole-Run program gets them through one `CodeIn lib (Extracted.program.link impl)` bridge per library (decided once).
   Extracted-free modules are also built once per lake build (not per row / extraction).
2. **One module per loop body / path** (`janus_run until [head]` + induction lemma per loop), so every module stays ≤ ~1 min:
   * `nat.montgomery`: entry→loop head (make/clear), loop iteration, loop exit (subVV / copy) — 3 modules per ISA.
   * window-4 / window-2: prologue + `stk.reserve` + x-normalisation; RR / one / powers[0..1]; precompute loop body;
     z/zz make + first window; inner-loop body (5 montgomery calls); outer-loop step; epilogue (final montgomery, cmp/sub,
     norm, defer) — ~7 modules per ISA per window size.
3. **Small contexts**: invariants as explicit equations on registers / frame slots (`janus_run [r…]` rewrite rules),
   disjointness as `Apart` (never unfolded disjunctions), values as `Nat` with `BitVec.ofNat` register equations.
4. `nat.montgomery` gets a **roomy** summary (`cap(z) ≥ 2n`, no `makeslice`): every call site in the windows passes such a
   `z` (3-index slices of `buf`, `make(2n)` results), so callers never see allocation in montgomery.
